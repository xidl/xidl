## API Versioning

A versioned IDL describes **one** contract: the latest state of the API. The
version history is declared next to it, and older versions are derived from
annotations instead of copied files.

```idl
#pragma xidlc package petstore

@version
enum ApiVersions {
    @rename("1.0") v1,
    @rename("2.0") v2,
};

struct Pet {
    string id;

    // introduced in v2
    @added(ApiVersions::v2)
    @optional string note;

    // deprecated at v2 and gone from then on
    @removed(ApiVersions::v2)
    string color;
};

interface Pets {
    @get(path = "/pets/{id}")
    Pet get(@path string id);

    @removed(ApiVersions::v2)
    @get(path = "/legacy")
    string legacy();
};
```

## Declaring the history

`@version` marks exactly one enum as the API version timeline. Its members are
the versions, **in declaration order**; the last member is the version the
source describes. Annotate a member with `@rename("...")` to give it a display
value such as a date or a semantic version:

```idl
@version
enum ApiVersions {
    @rename("2025-01") v2025_01,
    @rename("2025-06") v2025_06,
    @rename("2026-01") v2026_01,
};
```

The member name (`v2025_06`) is the stable machine name used in output paths
and selection flags; the value (`2025-06`) is what versioned documents carry.
Per-version documents ignore `#pragma xidlc version` and use the projected
version value as `info.version`.

## Lifecycle annotations

| Annotation | Meaning |
| --- | --- |
| `@added(Versions::vN)` | the declaration exists from that version onward |
| `@removed(Versions::vN)` | the declaration is removed at that version |

Both can appear on modules, type declarations (structs, unions, enums,
exceptions, typedefs, bitsets, bitmasks), struct/union members, enumerators,
bitmask values, interfaces, operations, operation parameters and interface
attributes.

Rules:

- Annotation order never matters. `@added(v2) @removed(v3)` and
  `@removed(v3) @added(v2)` describe the same interval.
- Each declaration carries at most one `@added` and one `@removed`, and
  `@added` must come strictly before `@removed`. Cycles such as
  `@added(v2) @removed(v3) @added(v4)` are rejected; declare a second member
  with a disjoint interval instead.
- A child's interval must stay inside its parent's. A member added in v1 of a
  struct added in v2 is an error.
- A surviving declaration must not reference a type that the projected version
  drops. Such a reference is reported with the declaration and the version.
- `raises(...)` entries are the one filtered position. An exception set has no
  annotation slot, so an operation raises a versioned exception only in the
  versions that declare it: older projections drop the entry.
- Root-qualified references (`::Models::Item`) keep pointing at the same
  declaration: projection rewrites them relative to the version module, so they
  resolve inside `module <version>` rather than at the file root.

Unimplemented versioning annotations (`@versioned`, `@renamedFrom`,
`@madeOptional`, `@madeRequired`, `@typeChangedFrom`,
`@returnTypeChangedFrom`, `@defaultVersion`) are rejected with an explicit
error instead of being silently ignored.

### Renames and other changes in phase 1

Phase 1 implements `@added` and `@removed` only. A rename or a shape change is
written as a **new member with a disjoint interval**; `@rename` keeps the wire
name stable when needed:

```idl
struct Pet {
    @added(Versions::v2)
    @removed(Versions::v3)
    int32 age;

    @added(Versions::v4)
    @rename("age")
    int32 age2_;
};
```

## Generated output

Projection wraps every version in `module <member-name> { ... }` and removes
the version enum and the lifecycle annotations, so generators never see a
versioned contract.

Code targets keep one module per version inside a single artifact:

```rust
// out/petstore.rs
pub mod v1 { /* structs, traits and servers for v1 */ }
pub mod v2 { /* structs, traits and servers for v2 */ }
```

OpenAPI and OpenRPC emit one document per version, named after the version
member:

```text
out/openapi_petstore.v1.json   # info.version = "1.0"
out/openapi_petstore.v2.json   # info.version = "2.0"
```

Every declared version is emitted by default. Narrow the output with
`--api-version` (one version) or `--api-versions` (a comma separated list, or
`*` for every version). Selection accepts the member name or the display value,
and rejects unknown versions with the list of declared ones:

```bash
xidlc gen openapi -o dist petstore.idl
xidlc gen openapi --api-version v1 -o dist petstore.idl
xidlc gen rust --api-versions v1,v3 -o dist petstore.idl
```

`xidl-build` exposes the same selection through `Builder::with_api_version` and
`Builder::with_api_versions`.

## Version change facts

Generate a language-neutral table for the complete timeline:

```bash
xidlc gen --out-dir out version-map petstore.idl
```

`out/petstore.version-map.json` contains direct changes between adjacent versions.
The same JSON value is available to generators and plugins as `props.version_map`.
Version selection does not narrow this table. Keys are sorted, indentation uses
two spaces, and the file ends with a newline.

Format 2 includes `declaration_id` in member, enumerator, union-case, operation,
and parameter descriptors. Request parameters are in `parameters`; output and
`inout` parameters also appear in `response_parameters`, keyed by location and
wire name. Each response binding contains an array of descriptors in source
order, including single-item bindings; this preserves repeated response headers.
An `inout` declaration has the same token on both sides. The synthetic
return value has no parameter identity. It distinguishes two declarations that happen to
have the same name, wire name, and type. The same source declaration keeps its
token across projections; two distinct declarations receive different tokens.
Tokens are opaque and local to the current source, so consumers must compare
them within one table and must not use them as persistent identifiers across
source revisions. Whitespace and comment changes preserve the tokens.

This changes the meaning of an omitted change: equal endpoint shapes alone no
longer hide a declaration replacement. Format 2 readers can distinguish that
replacement without recovering lifecycle annotations from projected HIR.
The table records facts; applications and optional adapter targets decide how
to convert values, resolve API versions, and route requests.

## Target support

Versioned contracts project into one module per version, so they need targets
whose module support renders a single module per API version:

| Target | Versioned contracts |
| --- | --- |
| `rust`, `rust-axum`, `typescript`, `typescript-rest` | supported |
| `openapi`, `openrpc` | supported, one document per version |
| `go`, `go-rest`, `rust-jsonrpc` | rejected with a clear error |

The remaining targets already misinterpret modules today (they repeat the
module wrapper or reference unqualified type names), so generation for them
fails loudly instead of emitting code that does not compile.

Serving several versions from one implementation (runtime conversion) is not
part of this feature; each version module is an ordinary generated server that
can be started on its own.


### Optional TypeScript version adapters

Generate the ordinary SDK and the adapter module independently:

```sh
xidlc gen --out-dir gen typescript-rest api.idl
xidlc gen --out-dir gen typescript-rest-adapters api.idl
```

The second target writes only `api.adapters.ts`. Ordinary SDK and server
artifacts are unchanged. It consumes projected HIR and format-2
`props.version_map`; the compiler core records facts and does not select an
application architecture.

The application resolves a version identifier and extracts HTTP parameters.
Pass a source-parameter envelope to `dispatch<Interface><Operation>(version,
raw, handler, adapters)`: the envelope uses IDL parameter names, while nested
JSON payloads retain wire keys. For example, `{ parcel: await request.json() }`
preserves unknown fields for served-version validation. Do not deserialize the
payload first: an ordinary schema may discard fields that an older version
must reject. Header, query and cookie parameters with the same wire name remain
separate source parameters.

Generated decoders recursively validate required fields, named types, sequences,
fixed arrays, records and unions before calling any conversion hook. Renamed
keys and flattened fields become model properties only after wire validation.
Unknown object keys and known fields belonging to another version are rejected;
flattened records retain their own arbitrary keys. Reserved `__proto__` object
keys are rejected before Zod can discard them.

Implement the generated `VersionAdapters` interface with pure decisions. Missing
hooks fail TypeScript compilation. Removed input members require `IGNORED`;
optional additions remain absent unless a simultaneous removal/addition requires
an explicit replacement decision. Conversion follows every adjacent step to
Head, short-circuiting on refusal. Handlers receive both the original version id
and its declared display value. Typed exceptions downgrade through every step;
framework errors preserve their identity.

`downcast<Interface><Operation>OutcomeTo<Version>` preserves the original Head
outcome when conversion fails. A write may already have committed: the application
owns idempotency, recording that outcome and rendering its declared refusal
error. Dispatch never retries the handler. `downcast<Type>(version, head,
adapters)` exposes the same complete chain for reachable result types.

Phase one rejects retired or replaced operation declarations, stream/upgrade
frame conversion, inherited structs, custom template types and inline union
case declarations whose nested identity is not exposed by the public map.
These are explicit generation errors, not silent field loss. This target does
not read version headers, choose routes, provide defaults or infer rename intent.
